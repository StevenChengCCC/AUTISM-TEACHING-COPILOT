# MaterialSpec boundary

Schema-version 1 generated artifacts use the discriminated `MaterialSpec` union as their
semantic source. Each subtype has closed typed content, instructional purpose, profile and
teacher-decision provenance, design constraints, validation results, and approval state.
Provider-authored dictionaries are not trusted as artifact semantics.

`V2MaterialSpecService` deterministically builds supported artifacts from a validated
`LessonSpec`. Cross-spec validation prevents token count/reward changes, data-sheet goal
drift, response-mode loss, and access-choice violations. AI may still propose wording in
the lesson package, but cannot populate or override protected MaterialSpec fields.

Historical `GeneratedMaterialDto.content` dictionaries are schema version 0. The explicit
compatibility adapter rebuilds supported schema-version 1 specs from the associated
LessonSpec; it never promotes unrestricted historical values into the canonical content.
Existing print-oriented `specification` objects remain compatibility metadata and are not
the new semantic contract.

No visual assets or printable renderers are generated by the MaterialSpec builder. Visual
asset requests remain typed metadata for a later round.

The first supported catalog mapping is:

- `blue_line_activity` -> personalized instructional activity;
- `help_card`, `break_card` -> communication card;
- `first_then_board`, `token_board`, `visual_timer`, `scenario_cards`, `choice_board`;
- `emotion_scale` -> regulation scale;
- `data_sheet` -> goal-specific data sheet;
- `session_summary`, `summary_template` -> lesson summary.

Other historical catalog types remain schema-version 0 compatibility artifacts until a
dedicated semantic subtype is implemented.
